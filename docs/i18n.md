# Internationalisation (i18n) — developer guide

BuyMeATee ships in 8 languages (ADR-019). This is the working guide for
developing with — and extending — the i18n system.

## Supported locales

| Locale | URL prefix | `<html lang>` | og:locale | Label (endonym) |
|---|---|---|---|---|
| en (default/fallback, source of truth) | /en | en-GB | en_GB | English |
| de | /de | de | de_DE | Deutsch |
| fr | /fr | fr | fr_FR | Français |
| es | /es | es | es_ES | Español |
| it | /it | it | it_IT | Italiano |
| ja | /ja | ja | ja_JP | 日本語 |
| ko | /ko | ko | ko_KR | 한국어 |
| pt | /pt | pt | pt_PT | Português (European) |

Single source of truth: [`i18n/locales.ts`](../i18n/locales.ts).

## Architecture at a glance

- **Library**: next-intl (App Router native). Plugin wired in `next.config.ts`.
- **Routing**: every page lives under `app/[locale]/` with
  `localePrefix: "always"` ([`i18n/routing.ts`](../i18n/routing.ts)). There
  are no unprefixed page URLs; `proxy.ts` 307-redirects legacy/unprefixed
  paths to the visitor's locale. API routes (`app/api/*`) and the auth route
  handlers (`app/auth/*`) stay unprefixed.
- **Detection priority**: URL > `NEXT_LOCALE` cookie > `Accept-Language` >
  `en`. The URL is always authoritative for the request. Signed-in users
  additionally persist `profiles.preferred_locale` via the language switcher.
- **Static generation preserved**: every layout/page calls
  `setRequestLocale(locale)` before any `getTranslations()`; marketing pages
  are SSG per locale (verify `●` markers in `next build` output). Supabase
  session refresh runs only for authed paths (see `proxy.ts`) — marketing
  requests never hit Supabase.
- **Messages**: `messages/<locale>/<namespace>.json`, one file per feature
  namespace. English is the source; all other locales are deep-merged over
  English at load time ([`i18n/load-messages.ts`](../i18n/load-messages.ts)),
  so a missing key can never render as a raw key or `undefined` — it renders
  English.
- **Typed keys**: the en catalog drives compile-time checking
  ([`i18n/en.ts`](../i18n/en.ts) + [`i18n/types.d.ts`](../i18n/types.d.ts)).
  An invalid `t()` key fails `tsc`.
- **Client bundles**: the root layout serializes only the `common` namespace.
  Feature areas add exactly what their client islands need via
  [`components/intl/client-messages.tsx`](../components/intl/client-messages.tsx)
  (`<ClientMessages namespaces={["gifts", "errors"]}>…`). Never pass the whole
  catalog to the client.

## Adding a translation key

1. Add the English string to the right `messages/en/<namespace>.json` file —
   full sentences, ICU interpolation (`{name}`), ICU plurals
   (`{count, plural, one {# supporter} other {# supporters}}`). Never
   concatenate fragments.
2. Use it: server → `getTranslations({ locale, namespace })`, client →
   `useTranslations(namespace)` (make sure the namespace is provided to the
   client via `ClientMessages` where needed).
3. Add the translation to each `messages/<locale>/<namespace>.json` (or leave
   it missing temporarily — English fallback covers it, and `npm run
   i18n:check` reports the gap; for locales marked complete in
   `messages/manifest.json` a missing key FAILS the check and the test suite).

## Adding a new language (e.g. pt-BR)

1. Add the code to `i18n/locales.ts` (locales array + label/lang/og/intl maps).
2. Create `messages/<locale>/` with the full namespace file set.
3. Extend the DB check constraints (`profiles.preferred_locale`,
   `gifts.locale`) with a new migration.
4. Add the Stripe Checkout locale mapping in `lib/payments/gifts.ts`.
5. Translate TS-structured content: blog articles
   (`lib/content/articles/<slug>.<locale>.ts` + registry) and legal documents
   (`lib/content/legal/*.<locale>.ts` + registry).
6. Run `npm run i18n:check`, tests and build; visual QA at 375/768/1024/1440.

## Formatting

All display formatting is locale-aware via
[`lib/i18n/format.ts`](../lib/i18n/format.ts): `formatMinorAmount(amount,
currency, locale)`, `formatDate`, `formatDateTime`, `formatRelativeTime`,
`formatNumber`, `formatPercent`. Amounts stay canonical integer minor units in
the DB; never hand-format numbers or dates, never store localized output.
The 2-arg `formatMinorAmount` in `lib/payments/currency.ts` is deprecated
(English-only shim).

## Errors and validation

Schemas and API routes carry stable codes, not sentences
([`lib/i18n/errors.ts`](../lib/i18n/errors.ts)):

- Schema field errors: `ErrorDetail = { code, params? }` where the code is a
  dot path in the `errors` namespace (e.g. `validation.goal.title` with
  `{max}`).
- API responses: `apiError(code, { status, params?, fields? })` from
  `lib/api/errors.ts` → `{ error: { code, params? }, errors?: { field: … } }`.
- Clients render with `useErrorMessage()`
  (`components/intl/use-error-message.ts`) — unknown codes fall back to the
  translated generic message; legacy string payloads pass through.
- Never surface raw Stripe/Supabase errors; log them server-side.

## Emails

Templates (`lib/email/templates.ts`) are async and take a `locale`; they use
`createTranslator` + `loadMessages` (no request context — safe in webhooks
and the queue worker). Locale resolution:

- Creator-directed emails: `profiles.preferred_locale` read **at delivery
  time** (`getUserEmailLocale`) — the queue stays semantic (type + payload).
- Supporter receipt: `gifts.locale`, captured at checkout from the UI locale.
- Fallback: English. CTA links are locale-prefixed; `<html lang>` is set.
- The Supabase magic-link email template is dashboard-managed and currently
  single-language (owner task; documented limitation).

## SEO

`lib/seo/metadata.ts`: self-referencing locale canonicals,
`alternates.languages` (hreflang for all 8 + `x-default` → en), og:locale.
Noindex surfaces (creator pages, gift confirmations, dashboards, admin,
sign-in) pass `noHreflang: true` and keep their noindex robots. Structured
data builders take the locale and set `inLanguage`. `app/sitemap.ts` emits
every indexable route × locale with full alternates. Blog slugs and creator
usernames are language-neutral and identical across locales.

## Content that is NOT translated

User-generated content is never machine-translated: display names, bios,
goal/update/wish-list titles and descriptions, supporter messages. Platform
labels around it are. Fictional Preview/Example content IS translated and
keeps its labels.

## Legal pages

English is the governing text. Translated legal pages render a
locale-visible notice ("translation for convenience — English governs").
**Every translated legal document requires professional legal review before
production reliance.** Structure lives in `lib/content/legal/`.

## Checks

```bash
npm run i18n:check   # parity: missing/extra keys, empty strings, ICU mismatches, duplicates
npm run test         # includes test/i18n-parity.test.ts and formatter tests
npm run build        # typed keys + SSG markers per locale
```

`messages/manifest.json` lists locales that must be complete (missing keys
become errors, not warnings).

## Feature checklist (new feature = all of these)

```
- UI strings extracted to the feature namespace (en) and translated in all locales
- Validation + API errors use codes from errors.json
- Metadata (title/description) translated; canonical/hreflang correct
- Emails (if any) rendered per recipient locale
- Accessibility labels / sr-only / alt text translated
- Currency/dates via lib/i18n/format (no hardcoded locale)
- Client namespaces provided via ClientMessages (don't ship the whole catalog)
- Mobile layouts checked in de (long words) and ja/ko (CJK)
- npm run i18n:check green; parity test green
```
